## 2. Persistence model (Drizzle, PostgreSQL)

Use UUID primary keys, `timestamptz` UTC, explicit enum/check constraints, foreign keys, and integer optimistic versions. PostgreSQL is authoritative. JSONB is permitted for versioned command/event payloads and snapshots, not as a substitute for indexed identity/scope/version columns. Migrations are forward-only; no hard deletion of audit data. Hash canonical JSON using RFC 8785 (UTF-8, SHA-256); persist canonicalization version.

`scope_binding` is a required structured value: `{project_id, package_id, plot_ids[], scope_version, design_revision, requirement_snapshot_id, evidence_version_ids[]}`. Persist normalized columns and a canonical hash; sort/deduplicate IDs before hashing. A shared evidence item is not reusable across a binding unless verified coverage explicitly includes every relevant plot/package/revision. No inferred coverage.

That complete `PACKAGE_GATE` binding is mandatory for package release/reliance, not for inventing a package before intake. The command/event scope is a discriminated union: `PACKAGE_GATE` has the fields above; `PROJECT_SCOPE` has verified project ID, scope version and relevant source/evidence IDs for masterplan/project-level facts; `PROVISIONAL_PLOT_SCOPE` has provisional case ID, exact plot IDs, initiator assignment, intake version and provenance, with project/package absent until linkage. A provisional case cannot satisfy a package gate. Linking preserves intake lineage and produces a new verified project/package binding; it does not manufacture previous approval applicability. Unknown package fields are never dummy IDs. Lock provisional cases by stable scope key in the same scope-lock class; a linkage command locks provisional and destination scopes in canonical key order.

## 3. Command contract and transaction boundary

All writes enter `POST /api/v1/commands/{commandName}`. Request envelope: `{command_id, command_name, aggregate_id, idempotency_key, expected:{aggregate_version,dependency_epoch}, scope_binding, payload, payload_schema_version}` plus authenticated session. Actor identity comes only from server authentication, never request payload. Optional issuer/signer are asserted identities with provenance and must be resolved/authorized; they are not replaced with actor. Responses are versioned JSON: `{command_id,result,event_ids,aggregate_versions,gate_evaluation_id?,replayed}`.

Route command name must match the envelope. Create commands use a caller-generated aggregate UUID with expected version zero; the DB still controls creation uniqueness and authorization. Pre-project envelopes use the provisional scope variant, nullable `project_id` in events, and cannot invoke package eligibility commands. Package-gate commands reject any non-package scope variant.

One PostgreSQL transaction at `SERIALIZABLE` (retry serialization failures a bounded 3 times, then return retryable conflict) performs: authenticate actor/role/scope; validate shape/version; lock deterministically; check idempotency; check expected versions and epoch; load coherent current facts; evaluate all local/global guards with unknown=deny; recheck assignments/expiry at injected command clock; validate dual approval hash; append assertion/evidence validation/state transition as applicable; increment versions/epochs; append event(s), ledger outcome and outbox row(s); save idempotent response; commit. No network/service call inside transaction. A failed command rolls back all success-side writes. Denial auditing is a separate minimal transaction after rollback, and must not imply success or create an outbox event.

Lock order, globally fixed: (1) idempotency row/key advisory lock; (2) project rows ascending UUID; (3) package/scope rows ascending `(project_id,package_id,scope_version)`; (4) aggregates ascending `(project_id,package_id NULLS FIRST,machine_id,aggregate_key,id)`; (5) dependency epoch rows ascending normalized scope key; (6) evidence logical IDs and versions ascending; (7) validator assignment/credential rows ascending; (8) approval rows ascending; (9) append-only inserts. Every command acquiring multiple lock classes follows this order. `SERIALIZABLE` does not replace explicit row locks and expected-version checks.

Material changes (expiry, revocation, suspension, scope/design/requirement change, evidence supersession, exemption revocation) increment affected epochs and set `revalidation_status=REQUIRED` atomically. Gate evaluation reads and locks all applicable dependencies; command rejects stale gate epoch/version vector even when machine says READY/APPROVED. Recompute never unlocks from event payload: handler obtains current facts and creates a fresh gate evaluation. Restore only with fresh independent verification and evaluation. Revalidation is an orthogonal overlay; it does not rewrite historical/authority machine status and never legally suspends/revokes an issued permit automatically.

## 4. Evidence, identity, corrections, dual control

Recording a report/fact is distinct from validation and package reliance. Authority approval/NOC, stamped technical document, legal authorization, exemption and waiver are regulated classes. Authority/legal/exemption validation requires a different eligible `STAKEHOLDER_MANAGER` with verified matching assignment/scope; structural stamp validation requires a different credentialed assigned `THIRD_PARTY_INSPECTOR`. Uploader differs from validator for regulated evidence. Technical signer may be uploader. Store actor/recorder, issuer (authority/organization making the assertion), technical signer, uploader and validator in separate fields; signer is not presumed to be recorder or issuer. AOR records another party's stamp and cannot manufacture the technical act. Recheck signer assignment/credential authorization at commit.

Validation binds immutable evidence version, class, project/scope, content hash and validity interval. Recording does not equal validation; generic document metadata does not validate. AOR_LEAD, SYSTEM_ADMIN and CLIENT_EXECUTIVE do not bypass evidence-class policy. Dual control means two distinct eligible human identities with required roles approving the same canonical command hash, scope hash and dependency/evidence versions; one person with multiple roles fails. Any changed input invalidates pending approvals.

Participant role pairs are exactly the YAML `dual_control_role_pairs`, including two **different** Client Executives for `S7-T07`. Missing eligible second person blocks the command. API route/envelope command names and schema identity must agree before hashing. A replayed successful result is history, not a new eligibility grant: clients must fetch current eligibility before any next action and cannot use an old success response as a gate token.

Admin correction is `CorrectAssertion`: append replacement, preserve original, require reason/source ID/actor/time/evidence links; never edit machine state or erase an assertion. Regulated correction additionally requires independent approval and ordinary evidence validation/current gate recomputation. Corrections cannot waive a gate.

**Fact recording versus action guard:** a new release/submit/resubmit/stamp/issuance/inspection activation/signoff/construction-start command is denied if current prerequisites, gate, authorization or dependency versions are unknown/invalid/stale. A `RecordHistoricalFact` command may record a claimed past receipt/approval despite inability to prove prerequisites, provided source/time/provenance are captured; it appends a quarantined assertion (`reliance_status=QUARANTINED`), no transition that claims dashboard authorization, no gate satisfaction/unlock, and an audit reason. Historical occurrence is not proof that dashboard allowed the action. Separate independent validation can later permit reliance without rewriting original history.

## 5. HTTP errors (stable schema)

Every error body: `{error:{code,message, retryable, command_id, details?}}`; never return secret or sensitive document contents. `details` contains stable field/path or guard identifiers, not a client-trusted authorization decision.

| HTTP | Code | Meaning |
|---|---|---|
| 400 | `SCHEMA_INVALID` | Missing/malformed field, unsupported payload schema, invalid enum. |
| 401 | `UNAUTHENTICATED` | No valid authenticated actor. |
| 403 | `FORBIDDEN` | Role/assignment/scope/independence/dual-control denial. |
| 404 | `NOT_FOUND` | Aggregate/package/evidence absent or not visible. |
| 409 | `IDEMPOTENCY_CONFLICT` | Same key, different canonical semantic payload or command identity. |
| 409 | `VERSION_CONFLICT` | Expected aggregate version mismatch. |
| 409 | `DEPENDENCY_STALE` | Epoch/vector/gate snapshot no longer current. |
| 409 | `STATE_CONFLICT` | No declared transition from current state/event. |
| 422 | `GUARD_DENIED` | Known false or unknown prerequisite; details list guard IDs and `UNKNOWN`/`FALSE`. |
| 422 | `EVIDENCE_INVALID` | Type/hash/scan/validity/coverage/validation failure. |
| 422 | `APPROVAL_INVALID` | Missing, stale, same-person or wrong-hash dual approval. |
| 429 | `RATE_LIMITED` | Retry after response header. |
| 503 | `TRANSIENT_FAILURE` | Serialization retries exhausted or DB unavailable; safe retry with same key. |

## 6. Idempotency and replay semantics

Semantic key scope is `(tenant_id, authenticated_actor_id, idempotency_key)`—command name is deliberately not part of the unique key, so reusing a raw key for another command is detectable. Payload hash is canonical hash of `{command_name, aggregate_id, expected versions, normalized scope binding, payload, schema_version}`. Exclude transport headers/request timestamp; include actor scope via key. First request reserves key transactionally. Same key + same hash returns the stored semantic result and original event IDs; `replayed=true` is response metadata and may differ from the original response. It does not re-evaluate or emit another event. Same key + different hash/command/aggregate returns `409 IDEMPOTENCY_CONFLICT`, no domain write. Different key but stale expected version returns `409 VERSION_CONFLICT`, never silently treats a semantically duplicate action as success. A concurrently in-flight matching key waits for winner then replays. Database uniqueness is final arbiter.

## 7. Atomic ledger and outbox

Successful domain writes, aggregate state/version, assertions/validations, dependency epoch changes, gate snapshot, workflow event(s), success ledger entry, outbox row(s), and idempotency response commit or roll back together. External delivery occurs after commit only. Dispatcher is at-least-once; handlers dedupe `(handler_name,event_id)` in same transaction as their projection/action writes. Failed delivery updates retry metadata, not immutable event. Do not persist a false successful transition if an outbox insert fails. Command denial audit captures denied attempt separately; never emit unlock/outbound side effect for denial. Logs/outbox are internal; there are no authority communication writes.
